# 004 — Read and write a field without touching its neighbours

**Level 1 · size M · concept: the read-modify-write primitive**
Starter: `004_fields.h`, `004_fields_test.c` · Notes: `notes/004.md` · Run: `make 004`

## Why this matters in firmware

Almost every peripheral setup is "change these bits and keep all the others". Fields of different
features share one register, so a sloppy write silently switches off a neighbour (for example turning
off an interrupt enable while you change a prescaler). Writing the primitive once, testing it
exhaustively and reusing it everywhere removes a whole class of bugs. In this item the tests are the
specification and the header is yours to fix.

## Words you need

- **Field**: a group of adjacent bits inside a register, described by a *mask* (already shifted into
  place) and a *position*.
- **Read-modify-write (RMW)**: read the register, change some bits, write it back.
- **Macro argument evaluation**: a macro pastes its arguments as text, so an argument can be evaluated
  more than once.

## The experiment

1. Run `make 004`. It fails. Read the message: it names the test that failed and what it expected.
2. Open `004_fields.h` and fix `FIELD_SET` (do **not** edit the tests). Run again. A different test
   will fail next. Repeat until every test passes. Keep a short log in `notes/004.md`: for each failure,
   what was wrong in your macro and what you changed.
3. Run `make 004 OPT=-O2` and `make 004 SAN=1`.
4. Read `test_value_too_wide` and `test_neighbours_untouched` again. They describe two different ways a
   write can damage another field. Which is which?

## Questions for your notes

1. List each bug the first attempt had, in your own words.
2. Why can `|=` alone never change a field that already holds a value?
3. The value being written is masked to the field width. What are the alternatives (assert, saturate,
   leave it to the caller), and what is the trade-off for firmware, where silent truncation hides a bug
   and a trap may be unacceptable?
4. What does `SAN=1` add compared with the plain run?

## Hints (open only when stuck)

<details><summary>Hint 1 — the "setting over an old value" failure</summary>

To store a new value you first need the field's bits to be zero. Which operation with a mask gives you
a register with exactly those bits cleared?
</details>

<details><summary>Hint 2 — the "bits outside the field changed" failure</summary>

Think about the value being written, not only the register. What if it has bits set beyond the field's
width? Which operation with the mask throws those away?
</details>

<details><summary>Hint 3 — keep the parentheses</summary>

In a macro, wrap each argument and the whole expression in parentheses, otherwise operator precedence
will bite you later.
</details>
