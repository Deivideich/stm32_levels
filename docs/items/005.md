# 005 — What type is this expression, really?

**Level 1 · size M · concept: integer promotion**
Starter: `005_integer_promotion.c` · Notes: `notes/005.md` · Run: `make 005`

## Why this matters in firmware

You constantly compute with small types: bytes of a protocol, 16-bit ADC samples, 8-bit register
fields. In C, arithmetic does **not** happen in those small types. They are first converted to a wider
one, and the result's type and value are not what most people expect. The surprises are silent: no
warning by default, and sometimes the language allows the compiler to assume it never happens
(undefined behaviour). This item has you find the rule by being wrong a few times, which sticks better
than reading it.

## Words you need

- **Integer promotion**: an integer type narrower than `int` is converted before arithmetic.
- **Usual arithmetic conversions**: what happens when the two operands still differ in type or signedness.
- **Undefined behaviour (UB)**: the language promises nothing (see item 001).
- **`_Generic`**: a compile-time type switch. The starter uses it as a tool to ask the compiler
  "what type does this expression have?".

## The experiment

**Part A — guess the type.** The table in the starter has ten expressions. Replace every `"?"` with
your guess (`"int"`, `"unsigned int"`, `"unsigned char"`, `"float"`, ...) **before** you run it. Do not look
the rule up first. Run `make 005`: each row says `ok` or `MISMATCH` and shows the actual type. Correct
your guesses, run again, and keep going until `make 005` exits 0. Count how many you got wrong on the first
attempt and write the number in your notes.

**Part B — guess the values.** Under the table, three values are printed. Predict each one and write it
next to the line, then run. After that run `make 005 SAN=1` and read what the sanitizer reports.

## Questions for your notes

1. State in your own words the rule you inferred about what happens to small types in arithmetic
   (two or three sentences).
2. Which row surprised you most, and why?
3. In `w + s`, `s` is `-1`. Predict the value of `w + s` and then verify it in code. What happened to
   the `-1`?
4. `vh * vk` is two 16-bit values multiplied. What is the mathematical result, what type does the
   expression have, and why is the printed value neither the mathematical one nor "wrapped to 16 bits"?
   Why is this undefined behaviour?
5. Give one realistic place in ADC, UART or timer code where you would meet this.

## Done when

- `make 005` exits 0, with your own guesses in the table.
- Part B predictions were written before running, and your notes say where they were wrong.
- You answered the five questions in your own words.

## Hints (open only when stuck)

<details><summary>Hint 1 — the rule, in one sentence</summary>

Before an arithmetic or bitwise operation, any operand whose type is narrower than `int` becomes `int`
(or `unsigned int` if `int` cannot hold all its values). Only then are the two sides compared for type.
</details>

<details><summary>Hint 2 — the cast row</summary>

A cast gives you a narrow type back, but only until the value is used in the next operation, where the
rule applies again.
</details>

<details><summary>Hint 3 — mixing signed and unsigned</summary>

When an `int` and an `unsigned int` meet, the `int` is converted to unsigned. Think about what `-1`
becomes.
</details>
