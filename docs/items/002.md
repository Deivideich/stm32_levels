# 002 — Who can see what?

**Level 1 · size M · concept: linkage and the symbol table**
Starter: `002_counter.c`, `002_counter.h`, `002_main.c` · Notes: `notes/002.md` · Run: `make 002`

## Why this matters in firmware

A module usually owns some hardware and some state. If any file can reach into another file's
variables, you can no longer say who changed a value, especially when an interrupt is one of the
writers. C gives you one tool for this: `static` at file scope. The compiler's symbol table then tells
you exactly what a module exposes, which makes it an honest way to check your own design.

## Words you need

- **Translation unit / object file (`.o`)**: one `.c` file compiled on its own, before linking.
- **Linkage**: whether other files may refer to a name. *External*: yes. *Internal* (`static`): no.
- **Symbol**: a name the linker knows about. `nm` lists them.
- **`nm` letters**: `T`/`t` code, `B`/`b` zero-initialised data, `D`/`d` initialised data,
  `U` needed from elsewhere. **Uppercase = exported, lowercase = private to the file.**
- **Declaration vs definition**: `extern uint32_t x;` says "it exists somewhere"; `uint32_t x;` creates it.

## The experiment

1. Run `make 002`. It prints `calls: 2`. The module has five things marked `(A)` to `(E)`.
2. Compile only the module and list its symbols:
   `gcc -std=c11 -c 002_counter.c -o /tmp/counter.o && nm /tmp/counter.o`
   Match each of `(A)` to `(E)` with a line of the output. For each one, write the letter `nm` gives it
   and why.
3. In `002_main.c`, add `extern uint32_t private_calls;` and print it with `printf`. Build. At which
   stage does it fail, compile or link? Read the message.
4. Decide which of `(A)` to `(E)` other files should be able to reach. Rework the module so that only
   functions are exported. `main` currently reads `total_calls`: give it a function to ask instead.
   Update the header and `main`.
5. Run `nm` on the object again. Save the output in `evidence/002/nm.txt`.

## Questions for your notes

1. `static uint32_t last;` inside a function and `static uint32_t private_calls;` at file scope: what do
   they have in common, and what differs? (Look back at item 001.)
2. Why could exposing `total_calls` as a variable hurt in firmware? Think of a value written in an
   interrupt and read in `main`.
3. What did `extern` change at compile time, and what did it not change at link time?
4. Looking at your final `nm` output: how can you tell, without reading the source, what the module's
   public interface is?

## Done when

- `nm` on the object shows **no uppercase `B` or `D`** symbols; the only uppercase `T` symbols are your
  public functions.
- `main` gets the call count through a function, and `make 002` still prints `calls: 2`.
- `evidence/002/nm.txt` exists and you answered the four questions.

## Hints (open only when stuck)

<details><summary>Hint 1 — what to expose</summary>

The header is the public contract: only what is declared there should be reachable. A function such as
`uint32_t counter_calls(void)` can return the value without handing out the variable itself.
</details>

<details><summary>Hint 2 — which things take <code>static</code></summary>

`static` also works on functions, not only on variables. Anything that is not part of the contract
should be private.
</details>
