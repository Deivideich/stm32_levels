# 003 — Bitfield or masks?

**Level 1 · size M · concept: describing a hardware register in C**
Starter: `003_bitfield_vs_masks.c` · Notes: `notes/003.md` · Run: `make 003`, then `make 003 OPT=-O2`

## Why this matters in firmware

A peripheral is controlled through 32-bit registers where each bit or group of bits means something
different, at positions fixed by the chip's datasheet. C bitfields look like the natural way to write
that, and a lot of vendor code uses them. But the C standard leaves important choices to the compiler:
the order of bits inside the word, how fields that cross a boundary are packed, and what size of
memory access is emitted. Masks and shifts say exactly where each field is, so nothing is decided for
you. This item makes you compare both on the same register.

## Words you need

- **Bitfield**: a struct member with an explicit width in bits (`uint32_t mode : 3;`).
- **Mask**: a number with 1s on the bits of a field (`0x0E` for bits 3:1).
- **Shift / position**: how far a field sits from bit 0.
- **Implementation-defined**: the compiler must choose and document a behaviour, but different compilers
  may choose differently. (Different from *undefined*: nothing is promised at all.)
- **Reserved bits**: bits the datasheet tells you to keep at 0.

## The experiment

Read the register description in the starter first (`CTRL`: EN, MODE, PRESC, IRQ_EN).

**Part A — predict.** With `mode = 5` and `presc = 9`, what is the whole 32-bit register in hex?
Work it out on paper from the datasheet table, write it next to the `printf`, then run `make 003`.
Does the compiler's layout match the datasheet? Does `sizeof` surprise you?

**Part B — masks.** From the datasheet (not from what you saw in Part A), define for each field a
`_POS` and a `_MSK` value.

**Part C — compare.** Write a loop over every combination of `en`, `mode`, `presc` and `irq_en`
(that is 2 × 8 × 16 × 2 = 512 combinations). For each one, build the register with the bitfield view
and with your masks, and `assert` that both raw values are equal. Remove the placeholder `assert(0, ...)`.
Run it with `make 003` and with `make 003 OPT=-O2`.

## Questions for your notes

1. Did the compiler's layout match the datasheet? Does the C standard guarantee that? (Search for
   "implementation-defined" in the standard or in the GCC manual's bitfield section.)
2. Name two situations where the same code could produce a different register value: a different
   compiler, a different target?
3. A bitfield write may be compiled into a read-modify-write of a different width than the register.
   Why could that matter for a hardware register? (You do not need to demonstrate it; reason about it.)
4. Which would you choose for firmware that must match a datasheet, and what do you give up?
5. Do your masks keep the reserved bits at zero? Why does the datasheet say "write 0"?

## Done when

- Your Part A prediction was written before running, and your notes say whether it was right.
- Your masks come from the datasheet, and the 512-combination test passes at `-O0` and `-O2`.
- You answered the five questions in your own words.

## Hints (open only when stuck)

<details><summary>Hint 1 — building the expected value</summary>

Write the register in binary with the bit positions above each digit, then put each field's bits in
its range. Convert to hex at the end.
</details>

<details><summary>Hint 2 — the compiler complains when assigning into a bitfield</summary>

With `-Wconversion`, putting a 32-bit value into a 3-bit field is flagged, because the value could be
too large. Masking the value to the width of the field first tells the compiler you know.
</details>

<details><summary>Hint 3 — structure of the loops</summary>

Four nested `for` loops, one per field, each running over that field's legal range.
</details>
